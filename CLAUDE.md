# CLAUDE.md

## Что это

`py_libs` — общая библиотека CLI-утилит (Select, Print, Menu, MyTable, Command, Notification,
Clipboard, CsvFile, FilesHandle, InputValidator, Rsync), подключаемая в другие проекты как git
submodule + uv workspace-зависимость. Используется как минимум в: py-private, py-vue,
py-bitbucket, py-files, py-sync-settings.

## Правило: рефакторинг проекта под py-libs

Когда пользователь даёт путь к другому проекту и просит "рефактор"/"добавь py-libs"/аналогичное —
это значит: найти в том проекте локальные дубли классов/утилит, которые уже есть в py_libs, и
заменить их использованием py_libs, устранив дублирование. Порядок действий:

### 1. Проверить подключение py-libs в целевом проекте

- `.gitmodules` содержит `libs/py-libs`
- `pyproject.toml`: `[tool.uv.workspace] members = ["libs/py-libs"]`,
  `[tool.uv.sources] py-libs = { workspace = true, editable = true }`, `"py-libs"` в dependencies
- Если submodule не инициализирован/устарел — сказать пользователю, он обновляет сам
  (`git submodule update --remote` и т.п.) — не трогать чужой git-стейт без спроса.

### 2. Аудит дублей

Для проектов среднего/большого размера (>10-15 файлов с классами) — сначала запустить fork-агента
на разведку: найти все файлы, дублирующие функциональность py_libs, и все их call-site'ы по
номерам строк, а не вычитывать всё в свой контекст самому. Явные кандидаты на дублирование —
классы/функции с именами вроде `Select`, `Clipboard`/`ClipboardManager`, `Notification`,
`InputValidator`, `pretty_print`/`pretty_table`, ручной `csv.reader`/`csv.DictReader`,
ручной `rsync`/`subprocess` boilerplate под sshpass.

### 3. Мигрировать — но с оглядкой на риски (см. "Грабли" ниже)

Для каждого найденного дубля:
- Найти ВСЕ call-site'ы (`grep -rn`), включая `tests/` — тестовый код тоже потребитель.
- Если потребителей мало (до ~10) — заменить импорты в каждом файле напрямую на `py_libs.X`,
  удалить локальный дубль-файл.
- Если потребителей много (десятки call-site'ов одной функции, например `pretty_print` в 25
  файлах) — НЕ переписывать все точки вызова. Оставить локальную функцию-обёртку с той же
  сигнатурой, но телом, делегирующим в `py_libs` (см. пример pretty_print/pretty_table в
  py-bitbucket). Это устраняет дублирование логики при нулевом риске для остальных файлов.
- Прежде чем удалить локальный файл — подтвердить `grep`-ом, что нигде больше не импортируется.
- Все правки — только после явного запроса пользователя на рефакторинг именно этого проекта;
  внутри одного согласованного рефакторинга можно действовать не останавливаясь между файлами.

### 4. Грабли, на которые уже наступали — проверять каждый раз

- **`Clipboard.write()` теперь сама шлёт desktop-уведомление** (plyer, title="Buffer",
  Wayland/X11-aware). Если рядом с локальным `ClipboardManager.write(...)` в коде сразу идёт
  свой explicit `Notification(...).notify(...)` — это станет ДВОЙНЫМ уведомлением после миграции.
  Убирать явный `Notification` вызов, если он там был именно ради "уведомить о копировании".
- **`Command.run`/`run_quiet` всегда делают `capture_output=True`** — НЕ использовать для команд
  с live/прогресс-выводом (`git clone`/`push`, `rsync --progress`, `bat`, что угодно с
  прогресс-баром). Замена молча убьёт видимый пользователю прогресс. Для rsync есть отдельный
  `py_libs.Rsync` (push/pull/local) — он НЕ захватывает вывод, прогресс стримится в терминал.
- **`CsvFile.read_csv()` использует `csv.DictReader`** — требует заголовок в первой строке.
  Перед заменой `csv.reader`(позиционного, без заголовка) проверить, есть ли реально заголовок
  в файле. Если это plaintext, расшифрованный из `.gpg` — учесть, что внешние pull/decrypt-flow
  (например `decryptFiles()` в py-sync-settings) могут молча перезаписать твою правку заголовка
  при следующей расшифровке. Если добавляешь заголовок в такой файл — сразу спросить пользователя
  про пересчёт `.sha256` и переширфование `.gpg` (`gpg -e -r <recipient> file`), не оставлять
  расхождение между plaintext и `.gpg`.
- **Не форсировать визуальный стиль `Print` (рамка из "=") туда, где его не было.** Сначала
  проверить `grep` по существующим `print("[color]...")`/`rich.print`/`Panel`-конвенциям в
  проекте. Если весь проект уже живёт на голом `rich.print` без рамок — миграция на `Print.info/
  success/error/warning` создаст визуальный разнобой. Либо спросить пользователя, либо не трогать
  чисто визуальные принты, ограничившись переносом только логики (CSV, Select и т.п.).
  `Print`-класс сам по себе (рамка "="*20) в py_libs менять/убирать без явной просьбы не надо.
- **Сохранять точную семантику при переносе на `InputValidator`.** `InputValidator.confirm()`
  по умолчанию YES на Enter; `get_bool()` зацикливается до валидного `y`/`n`. Если в проекте
  сейчас `input("... (y/n): ")` с семантикой "что угодно кроме 'y' — это отмена, без переспроса" —
  ни один метод `InputValidator` не совпадает 1-в-1. Мигрировать только точные семантические
  совпадения, остальное — оставить как есть или явно спросить.
- **Линтер проекта может быть не flake8.** Проверять `pyproject.toml`/`tool.ruff`/`.flake8` —
  например py-files использует `ruff` с `line-length = 88` и `fix = true` (автофиксит сортировку
  импортов при каждом запуске — это нормально, не откатывать).
- **`uv run pytest`/`uv run flake8` могут молча упасть на системный бинарник**, если пакет не
  в зависимостях проекта (uv фоллбэкается на `$PATH`). Если тестовый раннер падает с
  `ModuleNotFoundError` на что-то не связанное с правкой — это скорее всего пред-существующая
  проблема окружения проекта, а не следствие рефакторинга; не чинить её попутно без просьбы,
  но и не принимать эту ошибку как "тесты сломаны от моей правки" — сначала проверить руками
  (`uv run python -c "..."`), что фактическое поведение не изменилось.

### 5. Верификация — обязательно, не пропускать

- `mypy` (тем флагами, что уже настроены в проекте: как правило
  `--explicit-package-bases --ignore-missing-imports .`) — должно быть чисто.
- Линтер проекта (flake8 или ruff — см. выше) — сверять НОВЫЕ ли замечания появились (через
  `git show HEAD:file` до/после), а не пугаться пред-существующих длинных строк в нетронутых
  местах.
- Функциональный smoke-тест на реальных/тестовых данных — не только `ast.parse`/импорт. Для CSV —
  реальный round-trip записи/чтения. Для Clipboard — write+read сравнение. Для Select/меню —
  мок на `Select.select_fzf_one`/`select_with_fzf`, чтобы проверить диспетчеризацию без реального
  TTY (`fzf` не работает в headless-режиме — это нормально, `None`/ошибка ioctl ожидаемы).

### 6. Изменения в самом py-libs (если рефакторинг требует новой функциональности)

- Новый класс/метод — сначала посмотреть, нет ли уже похожего в другом проекте (например,
  `Clipboard` дублировался в 3 репозиториях с разной степенью "богатости" реализации — взяли
  самую функциональную версию за основу, а не первую попавшуюся).
  - Скачивание изменений в другой submodule-репозиторий из проекта, где я не менял py-libs —
    делать через `git fetch`/pull в его `libs/py-libs`, а не гадать; если пользователь говорит
    "сам обновлю" — не трогать, просто подождать и продолжить после подтверждения.
- `git commit` (новый коммит, не amend) + `git push origin main` в самом py-libs репо — это
  общий для нескольких проектов удалённый репозиторий. Всегда спрашивать подтверждение перед
  push, даже если до этого уже пушили в рамках той же сессии.
- Прогнать `flake8`/`mypy` на изменённый файл py-libs, `uv sync` в проекте(-ах), где тестируешь.
